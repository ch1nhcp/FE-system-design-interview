## TL;DR

Edge code runs close to users for quick request decisions.
Distant data and runtime limits can erase the latency gain.

```ts
// An edge function for an A/B test. It runs in the location closest to the user, with Web APIs only.
export default {
  async fetch(request: Request): Promise<Response> {
    const cookie = request.headers.get('cookie') ?? '';
    const variant = /(?:^|; )ab=(a|b)/.exec(cookie)?.[1] ?? (Math.random() < 0.5 ? 'a' : 'b');

    // Each variant is a separate cached page, so the edge can answer without the origin.
    const url = new URL(request.url);
    url.pathname = `/${variant}${url.pathname}`;
    const response = await fetch(new Request(url, request));

    const headers = new Headers(response.headers);
    headers.append('Set-Cookie', `ab=${variant}; Path=/; Max-Age=2592000; SameSite=Lax`);
    return new Response(response.body, { status: response.status, headers });
  },
};
```

## Key points

- Best for small, stateless decisions before cached content.
- Lightweight runtimes expose a limited API surface.
- Keep data nearby or compute close to the database.
- Respect CPU, memory, bundle and consistency limits.

## Trade-offs

| Strengths                | Weaknesses                      |
| ------------------------ | ------------------------------- |
| Short client round trips | Restricted runtime and APIs     |
| Lightweight startup      | Data may be far away            |
| Select cached variants   | Distributed debugging is harder |

## Interview questions

<InterviewQuestion question="What belongs at the edge, and what does not?">

Fast decisions that only need the request itself, cookies or small edge data: redirects, auth token checks, A/B bucketing, geolocation and header rewrites.
Heavy computation and work that needs a central database belong at the origin, close to the data.

</InterviewQuestion>

<InterviewQuestion question="How does edge differ from regional serverless?">

A serverless function usually runs in one region on a full runtime such as Node.js, with longer time limits and possible cold starts.
An edge function runs in many locations on a lightweight runtime that starts almost instantly, with stricter limits on CPU time, memory and APIs.

</InterviewQuestion>

<InterviewQuestion question="How do you personalize a page without losing CDN caching?">

Cache a small number of variants, such as per country or experiment bucket, and let the edge pick the variant from a cookie or header.
Render user-specific bits, like the account menu, on the client or in a separate uncached request.

</InterviewQuestion>

### Design details

- Code runs in hundreds of locations, so the round trip is short wherever the user is.
- Many edge runtimes use lightweight isolates and Web APIs; Node.js compatibility and startup limits depend on the platform.
- Best for fast, stateless logic in front of cached content: redirects, rewrites, auth checks, headers, A/B tests.
- Calling a single-region database from the edge adds back the latency it saved; keep data at the edge or near the origin.
- CPU time, memory and bundle size are tightly limited.

### How it works

The CDN deploys your function to all its locations.
A request is routed to the nearest one, where the function can answer directly, rewrite the URL, change headers, or fetch from the cache or the origin.
Isolate-based platforms reuse lightweight runtimes rather than booting a container for each request.

### Edge cases

- Global data consistency: edge key-value stores are often eventually consistent, so a write may not be visible everywhere at once.
- Randomness and time differ per location, which matters for experiments and caching keys.
- Some libraries depend on Node.js APIs and will not run at the edge.

### Common mistakes

- Making several round trips to an origin database from the edge for each request.
- Bundling large dependencies that exceed the size limit or slow every request.
- Varying the cache on too many headers, so the hit rate collapses.
