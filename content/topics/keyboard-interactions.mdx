## TL;DR

Keyboard users need predictable controls and visible focus.
Start with native elements and complete the keyboard contract of any custom widget.

## Key points

- Preserve native button, link and form semantics.
- Keep DOM order aligned with the visual task order.
- Use Tab between widgets and pattern keys within them.
- Avoid positive tabindex values and keyboard traps.
- Scope shortcuts and preserve text-entry behavior.

## Trade-offs

| Approach         | Strengths            | Weaknesses              |
| ---------------- | -------------------- | ----------------------- |
| Native control   | Built-in behavior    | Styling boundaries      |
| Composite widget | Efficient navigation | Full key contract       |
| Shortcut         | Faster repeat tasks  | Conflicts and discovery |

## Interview questions

<InterviewQuestion question="Why not make a div act like a button?">

A role alone does not add focusability, keyboard activation, disabled behavior or form semantics.
A native button supplies a stronger starting contract and avoids having to rebuild those behaviors correctly.

</InterviewQuestion>

<InterviewQuestion question="Should Tab visit every item inside a tab list?">

A composite pattern commonly exposes one tab stop and uses arrow keys to move inside the group.
Follow the appropriate pattern for focus, selection and activation instead of applying one rule to every kind of widget.

</InterviewQuestion>

<InterviewQuestion question="How should shortcuts behave inside an input?">

Avoid intercepting normal typing, composition or established browser and assistive-technology commands.
Scope shortcuts to an appropriate context and provide disabling, remapping or modifier behavior when a single-character shortcut requires it.

</InterviewQuestion>

### How it works

Sequential focus navigation follows focusable elements in a document's intended order unless custom logic changes that contract.
Native controls supply keyboard activation, while composite widgets need deliberate focus movement and state coordination.
Test an end-to-end task with keyboard-only input, including validation failures, dialogs and content updates.

### Edge cases

- A visually reordered layout can make its unchanged DOM tab sequence confusing.
- Roving focus and active-descendant patterns have different implementation contracts.
- A custom Enter or Space handler on a native button can trigger its action twice.

### Common mistakes

- Adding role and tabindex while omitting the corresponding keyboard behavior.
- Forcing a custom tab sequence with positive tabindex values.
- Treating a modal focus loop as acceptable without Escape or another usable close action.
