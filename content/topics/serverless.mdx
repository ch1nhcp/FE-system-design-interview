## TL;DR

Serverless functions run on demand and scale with traffic.
Cold starts and resource limits shape their trade-offs.

// app/api/subscribe/route.ts: a route handler deployed as a serverless function.
import { z } from 'zod';

const bodySchema = z.object({ email: z.email() });

// Created once per instance and reused across warm invocations.
const db = createDbClient({ url: process.env.DATABASE_URL, pool: { max: 1 } });

export async function POST(request: Request) {
  const result = bodySchema.safeParse(await request.json());
  if (!result.success) {
    return Response.json({ error: 'Invalid email' }, { status: 400 });
  }
  await db.subscribers.insert({ email: result.data.email });
  return Response.json({ ok: true }, { status: 201 });
}

## Key points

- The platform starts and scales function instances.
- Usage pricing suits bursts, less so steady heavy traffic.
- Keep durable state outside short-lived instances.
- Limit concurrency and pool downstream connections.

## Trade-offs

| Strengths              | Weaknesses                    |
| ---------------------- | ----------------------------- |
| Automatic scaling      | Cold starts                   |
| Usage-based cost       | Time and memory limits        |
| Less server operations | Connection limits and lock-in |

## Interview questions

<InterviewQuestion question="What is a cold start, and how do you reduce it?">

When no warm instance is free, the platform has to boot a runtime and load your code before handling the request.
Keep the bundle and dependencies small, initialize expensive clients lazily, prefer lighter runtimes, and keep critical functions warm with provisioned or minimum instances.

</InterviewQuestion>

<InterviewQuestion question="Why can serverless exhaust database connections?">

Hundreds of instances can start at once, and each opens its own connections, which quickly exhausts the database's connection limit.
Use a connection pooler, a database with an HTTP or serverless driver, and keep at most one connection per instance.

</InterviewQuestion>

<InterviewQuestion question="When would you not use serverless?">

For long-running work, steady high traffic where always-on servers are cheaper, persistent connections such as WebSockets, or latency-critical paths that cannot afford cold starts.

</InterviewQuestion>

<DeepDive>

### Design details

- No servers to manage: the platform starts, scales and stops instances for you.
- Cost follows usage, which suits spiky or low traffic, but steady high traffic can cost more than servers.
- Cold starts add from tens of milliseconds to seconds when no warm instance is available.
- Functions are stateless and short-lived: keep state in a database, cache or queue, not in memory.
- Each instance opens its own connections, so use a connection pooler or an HTTP-based database driver.

### How it works

The platform packages each function, and on a request it routes to an idle instance or starts a new one.
Instances handle one request (or a few) at a time, stay alive briefly after finishing, and are stopped when idle.
Front end frameworks compile SSR pages and API routes into such functions, often one per route.

### Edge cases

- Fan-out bursts can start thousands of instances and overwhelm downstream services; add queues and concurrency limits.
- Background work after the response may be killed; use the platform's `waitUntil` or a queue.
- Retries on failure can run the same event twice, so handlers should be idempotent.

### Common mistakes

- Keeping user sessions or caches in memory, which disappear between invocations.
- Opening a new database connection on every request.
- Shipping a huge bundle, which makes every cold start slower.
