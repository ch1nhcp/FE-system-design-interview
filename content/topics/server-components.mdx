## TL;DR

Server Components render data-heavy UI without shipping its code.
Small client components handle interaction.

'use client';
import { useTransition } from 'react';

export function AddToCart({ productId }: { productId: string }) {
  const [pending, startTransition] = useTransition();
  return (
    <button disabled={pending} onClick={() => startTransition(() => addToCart(productId))}>
      {pending ? 'Adding…' : 'Add to cart'}
    </button>

}

## Key points

- Run on the server at build or request time.
- Read data directly; keep state and effects on the client.
- Pass React-supported values across the boundary.
- Stream slow sections behind Suspense boundaries.

## Trade-offs

| Strengths              | Weaknesses                      |
| ---------------------- | ------------------------------- |
| Less client JavaScript | Server or build integration     |
| Data beside components | Explicit server/client boundary |
| Progressive streaming  | Navigations may need the server |

## Interview questions

<InterviewQuestion question="How are Server Components different from SSR?">

SSR renders client components to HTML on the server, then sends all their JavaScript to hydrate them.
Server Components are never hydrated: they render on the server only, and the browser gets their output, not their code.
They are usually used together: server components for the static and data-heavy parts, client components for interactivity.

</InterviewQuestion>

<InterviewQuestion question="Where should the server/client boundary sit?">

Keep components on the server by default, and move the smallest interactive leaf to the client, such as a button, a form or a menu.
Pass server-rendered content into client components as `children` instead of importing it, so it stays on the server.
Anything that needs state, effects, event handlers or browser APIs has to be a client component.

</InterviewQuestion>

<InterviewQuestion question="How does streaming improve perceived performance?">

The server sends the shell and fast sections immediately, with fallbacks where slow data is still loading.
Each `Suspense` boundary is filled in as its data resolves, on the same response, so users see and use most of the page sooner.

</InterviewQuestion>

### Design details

- Server components run at request or build time and never in the browser, so their code and dependencies stay off the bundle.
- They can be `async` and read databases, files or internal APIs directly, without a client-side fetch.
- They cannot use state, effects or browser APIs; those belong in client components marked `'use client'`.
- Props crossing to a client component must use React-supported serializable values; ordinary closures cannot cross.
- `Suspense` boundaries let the server stream slow parts later instead of blocking the whole page.

### How it works

The server renders the component tree into a serialized description of the UI, the RSC payload, plus HTML for the first load.
Client components appear in that payload as references to their JavaScript chunks, with the props to render them.
On navigation the client fetches only the new payload and merges it into the page without losing client state.

### Edge cases

- Importing a server-only module, such as a database client, into a client component leaks it to the browser bundle; mark such modules `server-only`.
- Context providers are client components, so wrap them as low in the tree as possible.
- Ordinary closures and unsupported class instances fail at the boundary; explicitly marked Server Functions cross as serializable references.

### Common mistakes

- Adding `'use client'` at the top of the tree, which turns the whole page into client components.
- Sequential `await`s in nested server components, creating a data waterfall; start requests in parallel.
- Using server components for highly interactive widgets that need instant feedback.
