For an API that accepts a partial JSON object and returns the updated resource or no body:

```ts
async function renameProject(id: string, name: string, etag: string) {
  const response = await fetch(`/api/projects/${encodeURIComponent(id)}`, {
    method: 'PATCH',
    headers: {
      'Content-Type': 'application/json',
      'If-Match': etag,
    },
    body: JSON.stringify({ name }),
  });

  if (response.status === 412) {
    throw new Error('Project changed. Reload before saving.');
  }
  if (!response.ok) throw new Error(`Save failed: ${response.status}`);
  return response.status === 204 ? null : response.json();
}
```

## Key points

- Model resource URLs with nouns and operations with HTTP methods.
- GET is safe; PUT and DELETE are idempotent by semantics.
- Check status before parsing; 204 has no response body.
- Use cache headers and ETags; invalidate stale client queries.
- Agree on errors, pagination and backward compatibility.

## Trade-offs

| Strengths            | Weaknesses        |
| -------------------- | ----------------- |
| Familiar HTTP tools  | Extra round trips |
| HTTP caching         | Overfetching      |
| Simple CRUD contract | Client-side joins |

## Interview questions

<InterviewQuestion question="When would you choose REST over GraphQL?">

When the UI maps cleanly to resources, payloads are predictable and HTTP caching matters.
A screen-specific aggregation endpoint can also remove waterfalls without introducing a GraphQL schema and execution layer.

</InterviewQuestion>

<InterviewQuestion question="Is it safe to retry a failed write?">

A network failure does not tell you whether the server applied the write.
Use method semantics and the API's contract: a create or payment often needs a server-enforced idempotency key, reused across retries of the same operation.

</InterviewQuestion>

<InterviewQuestion question="How do you prevent conflicting edits?">

Read the resource's strong ETag, then send it in `If-Match` on the write.
The server checks and updates atomically; a stale version returns 412 so the UI can reload, compare and resolve the conflict.

</InterviewQuestion>

### How it works

The client requests a representation of a resource, and the server applies authentication, authorization and validation before reading or changing it.
HTTP methods define the operation's semantics; JSON is a common representation format, not a requirement of REST.
Strict REST also includes hypermedia and other architectural constraints; many interview discussions use REST to mean resource-oriented HTTP APIs.

### Design details

- Model resources with nouns; use methods to express reads, creates, replacements and deletions.
- GET is safe; PUT and DELETE are idempotent by semantics, while POST and PATCH need an explicit retry contract.
- Check HTTP status before reading a body: `fetch` does not reject on 4xx or 5xx, and 204 has no body.
- Use cache headers and validators such as ETag; invalidate affected client queries after writes.
- Agree on error shape, pagination, optional fields and backward compatibility before building screens.

### Edge cases

- A successful DELETE can be followed by a 404 on retry while still being idempotent: the intended resource state is unchanged.
- Aborting a browser request does not guarantee cancellation of a server-side write.
- Personal responses need an explicit private caching policy so a shared cache cannot serve one user's data to another.

### Common mistakes

- Treating every response as JSON, including 204 responses.
- Retrying a non-idempotent operation after a timeout without duplicate protection.
- Changing an existing field's meaning without a compatibility plan for older clients.
