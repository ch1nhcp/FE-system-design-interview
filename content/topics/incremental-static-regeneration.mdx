## TL;DR

ISR serves cached HTML and regenerates pages as needed.
It trades some freshness for static delivery speed.

```tsx
// app/products/[id]/page.tsx (Next.js App Router)
export const revalidate = 3600; // time-based revalidation becomes eligible after one hour

// Build the most visited pages ahead of time; the rest are built on their first request.
export async function generateStaticParams() {
  const products = await getTopProducts(100);
  return products.map((product) => ({ id: product.id }));
}

export default async function ProductPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const product = await getProduct(id);
  return <ProductDetails product={product} />;
}
```

```ts
// Invalidate after saving; a currently viewed affected page can refresh immediately.
'use server';
import { revalidatePath } from 'next/cache';

export async function publishProduct(id: string) {
  await saveProduct(id);
  revalidatePath(`/products/${id}`);
}
```

## Key points

- Expiry can serve stale HTML while regeneration runs.
- On-demand APIs invalidate paths or tagged data.
- Prerender popular pages; generate the long tail on demand.
- Keep personalized or live data outside shared HTML.

## Trade-offs

| Strengths              | Weaknesses                      |
| ---------------------- | ------------------------------- |
| Fast shared HTML       | Temporarily stale content       |
| Handles traffic spikes | No private data in shared cache |
| On-demand long tail    | Regeneration support required   |

## Interview questions

<InterviewQuestion question="How is ISR different from SSR with a CDN cache?">

Both serve cached HTML and refresh it later, but ISR treats the page as a build artifact: it is generated once and reused until it expires or is revalidated.
SSR with `Cache-Control: s-maxage, stale-while-revalidate` gets a similar effect through HTTP caching, and works on any CDN.
ISR adds on-demand revalidation by path or tag and pre-building at deploy time.

</InterviewQuestion>

<InterviewQuestion question="Why can a published CMS edit remain invisible?">

The cached page is served until the revalidate window passes, and the first visit after that still gets the old version while the new one builds.
Invalidate the path from the CMS publish hook, and keep the time-based window as a safety net.
In the Next.js App Router, a Route Handler marks a path for revalidation on its next visit.
A Server Function can update an affected currently viewed page immediately; neither call should be described as eagerly rebuilding every related path.

</InterviewQuestion>

<InterviewQuestion question="Which pages are a good fit for static generation?">

Pages that look the same for every visitor and change much less often than they are viewed: docs, blog posts, marketing pages and product catalogs.
Pages with per-user data or second-by-second data need SSR or client-side fetching for those parts.

</InterviewQuestion>

<DeepDive>

### Design details

- Static pages are the fastest to serve: no rendering per request, just a file from the nearest CDN location.
- ISR follows stale-while-revalidate: the first visit after expiry still gets the old page and triggers a rebuild.
- On-demand invalidation marks a path stale after a data change; regeneration timing depends on the framework API.
- Build only the popular pages up front and generate the long tail on first request, to keep builds short.
- Not for personalized or real-time content; combine with client-side fetching for the parts that must be live.

### How it works

At build time the framework renders each known page to HTML and stores it.
A request is served from the cache; if the page is older than its `revalidate` time, the framework regenerates it in the background and swaps it in for the next visitor.
Unknown paths can be rendered on their first request and then cached like the others.

### Edge cases

- The call site matters: a Route Handler marks the path for its next visit, while a Server Function can update affected UI currently being viewed; neither is an eager bulk prerender job.
- Regeneration can fail, for example when an API is down; the old page keeps being served, so monitor failures.
- Pages that depend on each other, such as a product page and a category list, need their own revalidation, usually grouped with cache tags.
- Very large sites still need care with build times and storage for millions of pages.

### Common mistakes

- Putting user-specific data in a statically generated page.
- Setting a tiny revalidate time, which turns ISR into SSR with extra complexity.
- Forgetting on-demand revalidation, so editors wait for the timer to see changes.
