## TL;DR

A WebSocket upgrades HTTP to a persistent, two-way connection.
It has low latency and small frames, but the app owns recovery and resync.

```ts
type Connection<Out> = { send: (message: Out) => void; close: () => void };

export function connect<In, Out>(url: string, onMessage: (message: In) => void): Connection<Out> {
  let socket: WebSocket | undefined;
  let reconnectTimer: ReturnType<typeof setTimeout> | undefined;
  let attempt = 0;
  let closedByUser = false;

  const open = () => {
    if (closedByUser) return;
    socket = new WebSocket(url);
    socket.addEventListener('open', () => {
      attempt = 0;
    });
    socket.addEventListener('message', (event) => onMessage(JSON.parse(event.data) as In));
    socket.addEventListener('close', () => {
      if (closedByUser) return;
      // Reconnect with exponential backoff and full jitter.
      const delay = Math.random() * Math.min(30_000, 1000 * 2 ** attempt);
      attempt += 1;
      reconnectTimer = setTimeout(open, delay);
    });
  };

  open();
  return {
    send: (message) => {
      // A real app queues messages while reconnecting instead of dropping them.
      if (socket?.readyState === WebSocket.OPEN) socket.send(JSON.stringify(message));
    },
    close: () => {
      closedByUser = true;
      clearTimeout(reconnectTimer); // a reconnect may be waiting in its backoff delay
      socket?.close();
    },
  };
}
```

## Key points

- Both sides send on one persistent connection.
- Frames add 2 to 14 bytes after the handshake.
- Add heartbeats, backoff, IDs and delivery guarantees.
- Scale broadcasts with pub/sub and long idle timeouts.
- Best for chat, collaboration, games and trading.

## Trade-offs

| Strengths                | Weaknesses                   |
| ------------------------ | ---------------------------- |
| Low latency both ways    | App owns recovery and resync |
| Small message overhead   | Stateful servers and deploys |
| Text and binary messages | Some proxies block upgrades  |

## Interview questions

<InterviewQuestion question="How do you handle a dropped WebSocket connection?">

Detect it from the `close` event and from a heartbeat, because a dead TCP connection can stay silent for minutes.
Reconnect with exponential backoff and jitter, then resubscribe and fetch what was missed using the last sequence number the client saw.
Queue outgoing messages in the meantime and show the connection state in the UI.

</InterviewQuestion>

<InterviewQuestion question="How do you scale WebSockets across many servers?">

Each connection lives on one server, so publish messages to a shared pub/sub layer, such as Redis, Kafka or a managed service, that every server subscribes to.
Raise load balancer idle timeouts and keep connections alive with heartbeats.
On deploys, drain connections gradually and let clients reconnect with jitter to avoid a thundering herd.

</InterviewQuestion>

<InterviewQuestion question="Which transport would you choose for chat?">

WebSockets: users send and receive often, and typing indicators need low latency both ways.
SSE plus normal `POST` requests is a simpler option when sending is rare.
Long polling is the fallback when neither gets through the network.

</InterviewQuestion>

### Design details

- Full duplex: both sides send messages on one long-lived connection.
- After the handshake each message adds only 2 to 14 bytes of framing instead of full HTTP headers.
- No built-in reconnection, message ids or delivery guarantees; you add heartbeats, backoff and resync.
- Each connection lives on one server, so broadcasting needs pub/sub across servers, and load balancers need long idle timeouts.
- Best for chat, collaboration, multiplayer and trading, where both sides talk often.

### How it works

The client sends a `GET` with `Upgrade: websocket`, `Connection: Upgrade` and a random `Sec-WebSocket-Key`.
The server answers `101 Switching Protocols` with `Sec-WebSocket-Accept`, derived from that key.
From then on both sides exchange frames on the same connection until one of them closes it.

### Edge cases

- Authentication: browsers cannot set custom headers on the handshake, so use a cookie or send a short-lived token in the first message. Avoid tokens in the URL, which end up in logs.
- Backpressure: `bufferedAmount` grows when you send faster than the network can carry, so slow down or drop low-value messages.
- Heartbeats: the browser API does not expose protocol pings, so send small application-level ping messages.

### Common mistakes

- Not checking the `Origin` header on the server, which allows cross-site WebSocket hijacking.
- Using `ws://` instead of `wss://` in production.
- Trusting incoming messages without validating them.
